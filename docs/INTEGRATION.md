# Интеграция с «МойСклад»

Сайт читает данные аккаунта «Бункера» через JSON API remap 1.2 и ничего не
выдумывает сам. Все привязки аккаунта ProHook удалены: состав типов цен,
 служебных складов и имён доп. полей задаётся переменными окружения.

## Безопасность

- Токен — только сервер: `NUXT_MOYSKLAD_TOKEN` (или `MOYSKLAD_TOKEN`) читают
  исключительно серверные сервисы (`server/services/moysklad*.ts`). В клиентский
  бандл и в `NUXT_PUBLIC_*` он не попадает; в логах не печатается.
- Изображения товаров отдаются через серверный прокси
  `/api/products/:id/images/:n` — URL с токеном не раскрываются браузеру.
- `.env` в `.gitignore`; в репозитории — только `.env.example` без секретов.

## Что и как сайт читает

| Данные «МойСклад» | Endpoint | Настройка |
| --- | --- | --- |
| Склады (магазины сети) | `entity/store` | города = группы складов (`pathName`); служебные скрываются `MOYSKLAD_INTERNAL_STORES` (имена) и `MOYSKLAD_INTERNAL_STORE_PREFIXES` (префиксы, напр. `РЦ`); архивные не выгружаются |
| Группы товаров | `entity/productfolder` | классификация корневых папок — `shared/legal/classification.ts` |
| Товары | `entity/product?filter=archived=false` | публикация по доп. полю `MOYSKLAD_ATTR_PUBLISH` (булево; поле отсутствует → публикуются все), имя — `MOYSKLAD_ATTR_SITE_NAME` |
| Цены | `salePrices` товара | порядок типов цен — `MOYSKLAD_PRICE_TYPES` (через запятую); для магазина берётся первый тип с ненулевой ценой; без переменной — первый ненулевой тип товара |
| Остатки | `report/stock/bystore` | точный остаток = stock − reserve; пороги подстановки: 0 «нет», 1 «мало», 2–3 «в наличии», 4+ «много» |
| Бонусная программа | `entity/bonusprogram` | выбор при нескольких активных: `MOYSKLAD_BONUS_PROGRAM_ID` или `MOYSKLAD_BONUS_PROGRAM_NAME`, иначе первая активная |
| Контрагент и баланс | `entity/counterparty` | поиск по телефону (контекстный search + сверка по цифрам номера) |

Снимок каталога кешируется на 5 минут с фоновой синхронизацией
(`server/services/catalog-cache.ts`).

## Порядок подключения

1. **Токен.** online.moysklad.ru → Профиль → API-токены → создать. Права
   достаточны только на чтение (сайт ничего не пишет в учёт).
2. **`.env`.** Вписать `NUXT_MOYSKLAD_TOKEN`, **удалить**
   `MOYSKLAD_SNAPSHOT_PATH` (иначе сайт останется на фикстуре).
3. **Сверка выгрузки.** `npm run catalog:sync` выводит количества
   товаров/категорий/магазинов. Затем открыть сайт и проверить:
   - корневые папки каталога соответствуют классификации
     (`shared/legal/classification.ts`): неизвестный корень НЕ публикуется —
     при необходимости добавьте ключ-имя папки в `ROOT_CATEGORY_CLASSES`;
   - типы цен подставляются верно (укажите `MOYSKLAD_PRICE_TYPES` явно);
   - служебные склады скрыты (пополните `MOYSKLAD_INTERNAL_STORES` /
     `MOYSKLAD_INTERNAL_STORE_PREFIXES`);
   - города собираются из групп складов (`pathName` в «МойСклад»).
4. **Доп. поля (необязательно).** Создайте в «МойСклад» булево поле
   «Показать на сайте» (управление видимостью товара) и текстовое
   «Название для сайта» (публичное имя вместо учётного). Имена можно
   переопределить env-переменными `MOYSKLAD_ATTR_*`.

## Бонусная программа (только чтение)

Подтверждённый механизм «МойСклад» (JSON API remap 1.2): сущность
`bonusprogram` хранит курсы и лимиты (`earnRateRoublesToPoint`,
`spendRatePointsToRouble`, `maxPaidRatePercents`, `earnWhileRedeeming`),
баланс контрагента — поле `bonusPoints`, участие — `bonusProgram`.
Loyalty API 1.0 обычным аккаунтам недоступен и не используется.

Выбранная модель (по решению владельца, как у ProHook):

- сайт **читает** правила программы и баланс контрагента и показывает их
  в личном кабинете и на странице брони;
- **начисление и списание бонусов выполняет персонал «МойСклад» на кассе** —
  сайт не создаёт бонусные транзакции и не списывает баллы дистанционно;
- привязка аккаунта сайта к контрагенту — по номеру телефона при
  регистрации/входе (best-effort, без создания контрагентов); контрагент
  заводится персоналом при выпуске карты в магазине;
- «Заказы покупателя» и контрагенты под брони в «МойСклад» не создаются:
  брони хранятся на сайте (`.data/reservations`), персонал видит их через
  Telegram-уведомление (опционально) и задачу в «МойСклад» (fallback) либо
  в инбоксе сотрудника на сайте (`/account`, allowlist-телефоны в
  `STAFF_INBOX_PHONES`).

## Уведомления о резервах (опционально)

1. Создайте Telegram-бота (@BotFather), узнайте chat_id получателей.
2. `TELEGRAM_BOT_TOKEN` + `TELEGRAM_RESERVATION_CHAT_IDS` (через запятую) —
   уведомления о резервах; `NUXT_TELEGRAM_BOT_TOKEN` + `NUXT_TELEGRAM_CHAT_ID` —
   заявки партнёрства.
3. При настроенной доставке формы требуют отдельное согласие на передачу
   данных через api.telegram.org; без неё запрос сохраняется и уходит
   задачей исполнителю `MOYSKLAD_NOTIFY_EMPLOYEE_ID` (или владельцу токена).

Проверка: отправьте тестовую бронь — в `.data/reservations` появится запись,
в Telegram (или задачах «МойСклад») — уведомление.

## Фикстурный режим (разработка и e2e)

`MOYSKLAD_SNAPSHOT_PATH=./tests/fixtures/catalog.json` подменяет каталог
демо-снимком, а `/api/account/loyalty` — детерминированными тестовыми
данными (`tests/fixtures/catalog.json` + `server/services/moysklad-bonus.ts`):
телефон `+7 900 000-00-01` → контрагент «Тестовый покупатель», баланс 500,
программа «Тестовая бонусная программа» (50 ₽ = 1 балл, 1 балл = 1 ₽,
до 50% покупки). В production-конфигурации переменная отсутствует и ветка
недостижима — фиктивных балансов не бывает.

## Что проверить после подключения реального аккаунта

- видимость поля `bonusPoints` у контрагентов токеном (зависит от тарифа
  «МойСклад» и прав токена);
- фактические имена типов цен и корневых папок (вывод `catalog:sync`);
- список служебных складов;
- работу прокси изображений (у товаров должны быть загружены картинки);
- при скрытии отдельных подкатегорий (например, энергетиков) — внести их id
  в `HIDDEN_SUBCATEGORY_IDS` (`shared/legal/classification.ts`).
